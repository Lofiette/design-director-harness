# Контракт адаптера непрерывности для агентского хоста

Статус: контракт адаптера, не подключённые hooks. `continuous-memory` v0.1 предоставляет локальные операции; host должен явно вызвать их и сохранить доказательства результата. Нельзя объявлять автоматическую синхронизацию или полный захват диалогов по одному наличию файлов.

## Наблюдение при старте и смене конфигурации

Адаптер фиксирует доступные фактические сведения:

| Поле | Надёжное значение |
|---|---|
| Host ID/version | Native runtime metadata/configuration с source locator |
| Provider/model ID/revision | Metadata API/host, различая alias и конкретную revision |
| Tools digest | Хеш реально доступного списка/схем, если он раскрыт |
| Context policy revision | Наблюдаемая версия pruning/compaction policy; иначе `null` |
| Skills catalogue | Активный provider, разрешённый scope, фактически выбранный skill source/hash и покрытие |
| Observed at | Timestamp с часовым поясом и источник наблюдения |

Самоназвание модели, догадка по стилю ответа и факт выхода нового релиза не подтверждают обновление активной сессии. Если сервис скрывает revision за постоянным alias, она остаётся `null`. Известно только то, что было наблюдено.

Сохранить fingerprint в immutable history и указатель последнего наблюдения в производном состоянии экземпляра. При сравнении не считать `observed_at` или путь отчёта изменением модели. Изменившийся host/toolset/context policy — изменение конфигурации с самостоятельным основанием. Сам переход поля из `null` в значение — новая наблюдаемость, не доказательство обновления.

## Отдельный контракт каталога

Наблюдение каталога хранит `coverage: complete_for_declared_scope | partial | unknown`, declared scopes, discovered entries, source evidence и exclusions. Полнота возможна только для явно перечисленного scope. Repository manifest, папки на диске и active provider selection не смешиваются.

Каждая наблюдаемая запись связывает имя навыка, выбранный provider/path, revision или content hash, owner/editability и precedence при дублировании. Если discovery не проведён, `skills_catalog_digest` fingerprint остаётся `null`; нельзя подставлять хеш пустого реестра. Отдельный `ddh-skill-registry/1` v0.1 служит реестром известных процедур и имеет строгую собственную схему.

## Захват источников до сжатия контекста

Если хост предоставляет pre-compaction hook:

1. Получить доступную исходную историю в пределах разрешённого экспорта: сообщения, пользовательские файлы, наблюдаемые результаты инструментов, решения и состояние задачи. Не считать пересказ полным исходником.
2. Указать source ID, revision/cursor, покрытый диапазон, точные границы и пропуски. Недоступные сообщения, внутренние рассуждения и скрытый системный контекст не реконструировать.
3. Сохранить исходные байты в durable source store; вычислить SHA-256 и размер; выполнить read-back. Если доступна только локальная staging-запись, статус — `local_only/remote_pending`, не «синхронизировано на устройства».
4. Создать event с immutable raw reference и stable ID. Только после подтверждённого сохранения строить compact handoff: цель, актуальное состояние, решения, evidence, открытые вопросы и следующая операция.
5. Сохранить handoff отдельно как производную проекцию, не удаляя source bytes. Source hash и revision позволяют обнаружить устаревшую ссылку при продолжении.
6. Передать компактный handoff в поддерживаемый native resume mechanism. Само сохранение текста в repo не означает, что host автоматически его прочитал.

Если hook отсутствует, использовать доступные события task completion/checkpoint/manual export и явно записать частичное покрытие. Не обещать захват последнего сообщения перед произвольным закрытием сессии. Сбой сохранения фиксируется как `capture_failed`; адаптер не подтверждает успешный handoff. Возможность задержать compaction зависит от реального контракта хоста и не придумывается.

Захват не должен включать токены, credentials или другие служебные секреты из среды. Private source archive не публикуется вместе с блогом. Полное сохранение доступного профессионального исходника и публичная редакция — разные артефакты с явной связью.

## Стабильные идентификаторы и повторы

Рекомендуемая основа capture ID: namespace владельца + source system + stable source ID + source revision/cursor range + версия протокола захвата. Хешировать каноническое представление этих полей. Не включать текущее время повторной попытки и случайный ID агента: retry не должен создавать новое событие.

Если источник не предоставляет stable revision, допустимо использовать digest точных исходных байтов вместе со stable locator и диапазоном. Явно записать эту схему. Для изменённого источника создаётся новый capture event с новой revision; старый сохраняется.

`run_id` рабочего сценария — идентификатор реального выполнения, независимый от повторов анализа/импорта. `model_observation_id` может включать fingerprint без timestamp и стабильный host-session transition ID. Повтор одного native события должен возвращать первоначальный результат; несовпадающее содержание под тем же ID — конфликт.

Не выдавать новое время захвата за время исходного события. Сохранять unknown occurrence-time как `null`. `occurred_at`, `captured_at`, семантическая validity и фактическое время обработки различаются.

## Перенос между устройствами

Локальная directory lock CLI сериализует записи только одного store. Для нескольких устройств нужен существующий Git/API sync с conditional write по ожидаемой revision или отдельный transactional service. Не использовать общий сетевой каталог как гарантию распределённых транзакций.

Сохранение считается доступным другому устройству после подтверждённой remote revision и read-back/разрешения source locator. При конфликте сначала сверить remote state и исходные события; не выполнять force overwrite. Между владельцами источников хранить ссылки, а не второй изменяемый канон.

## Минимальная приёмка адаптера

- Новая сессия читает короткое ядро и карту источников, не весь архив.
- Сохраняется доступный оригинальный эпизод, затем завершается/сжимается сессия; новая восстанавливает его через обзор и конкретный source ID.
- Повтор native callback не дублирует факт или успешный workflow.
- Новая известная revision модели вызывает scan; скрытая version остаётся unknown.
- Каталог с дубликатами показывает реально выбранный источник, а отсутствие discovery не превращается в полный scan.
- Ошибка синхронизации не объявляется успешной cross-device памятью; прежние источники остаются доступны.

Каждый PASS должен иметь host/version, model observation, input revisions и evidence. Пока такие прогоны отсутствуют, статус hooks и live recovery — `not_run`/`not_connected`, а не вывод о ненадёжности конкретной модели.
