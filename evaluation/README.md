# Проверка Design Director Harness 5.0

Эталонные семейства взяты из Product OS 4.1.0, тег v4.1.0, commit 1870f6fc200638a200348762004d24c2803f93b1. В отдельной копии тега v4.1.0 файлы `evaluation/executable/cases/{micro_copy_change,design_system_ui_implementation,compaction_recovery}.json` сохраняют исходные сценарии. Здесь сценарии сформулированы нейтрально для сравнения трёх конфигураций.

| Сценарий | Условие приёмки | Офлайн-проверка сборки |
|---|---|---|
| Мелкая правка | Точный новый текст, один целевой файл, focused check. Служебные записи и дополнительные попытки считаются отдельно. | Маршрут мелкой правки в обоих пакетах. Нативный выбор маршрута проверяется live. |
| Сложный UX | Существующие компоненты и токены, нужные состояния, восстановление после ошибки, клавиатура, фокус и проверка при двух ширинах. | Наличие и побайтовое равенство матрицы приёмки в обоих пакетах. Нативная оценка UX проверяется live. |
| Прерывание | После нового запуска восстановлены цель, границы, доказательства и следующая операция. При расхождении с артефактом есть явный отказ. | Чекпоинт и возобновление через разные процессы. Проверяется изменение артефакта, идентификатора и тела чекпоинта. |

## Протокол live-сравнения

Сравнить чистый Codex, Product OS 4.1 и DDH 5.0 на одинаковых исходных файлах, задаче, модели, reasoning effort и песочнице. Для каждого прогона использовать отдельный профиль и свежую копию проекта. Оценивать изменения и артефакты по общей рубрике. Сохранять сырые результаты локально по условиям допуска.

Для каждого сценария записывать PASS/FAIL/BLOCKED, дефекты, время до принятия, число попыток, объём служебных действий и input/cached/output, если хост их сообщает. При малой выборке сравнивать только конкретные задачи. Отдельный нативный smoke DSH проверяет каталог, загрузку ядра с учётом pruning и доступные операции. Сходство Markdown-пакетов не проверяет поведение модели и нативных провайдеров.

### Подготовка

Из папки DDH создайте девять рабочих копий. `--out` принимает новый путь, поэтому повторный замер можно провести рядом с предыдущим.

```powershell
$ddhSuite = Join-Path $env:TEMP 'ddh-bench-01'
node evaluation/bench.mjs prepare --out $ddhSuite
```

В `plan.json` перечислены прогоны. В каждой папке прогона есть отдельный `project/` и шаблон записи для проверяющего. Карточки из `operator/` находятся снаружи проекта. Передавайте агенту только текущий запрос, а оценщику — критерии и артефакты.

| Конфигурация | Что подготовить |
|---|---|
| `codex-plain` | Чистый временный `CODEX_HOME` и исходный проект. |
| `product-os-4.1` | Из проверенного checkout 4.1 выполнить `python tools/cpt_dist.py install --project <project> --mode local --plugin-scope none --enforcement-mode audit`. В отдельном временном `CODEX_HOME` зарегистрировать marketplace из **корня** checkout и включить `cpt-core@product-os` и `cpt-design-ui@product-os`. Записать, подтверждено ли исполнение хуков. |
| `ddh-5.0` | Из папки DDH выполнить `node tools/ddh.mjs install --project <project>` и открыть проект с отдельным временным `CODEX_HOME`. |

Сверьте каталоги навыков и настройки модели для трёх конфигураций. Сохраните версию CLI, модель, effort, настройки песочницы и профиль запуска рядом с отчётом. Проверяйте, что пользовательские каталоги навыков не добавили лишние различия. Рабочие копии не содержат Git-репозитория. Если используете `codex exec`, в таких копиях нужен `--skip-git-repo-check`.

### Снимки и оценки

Снимок `initial` делается после установки профиля и до первого запроса. Стенд проверяет исходные файлы по общей фикстуре. Пример для UX:

```powershell
node evaluation/bench.mjs capture --suite $ddhSuite --run ddh-5.0-ux --phase initial
# Передать prompt из operator/ux.json и дождаться первого ответа
node evaluation/bench.mjs capture --suite $ddhSuite --run ddh-5.0-ux --phase first
# Передать secondPrompt в тот же чат
node evaluation/bench.mjs capture --suite $ddhSuite --run ddh-5.0-ux --phase final
node evaluation/bench.mjs report --suite $ddhSuite
```

У `copy` два снимка, `initial` и `final`. В `recovery` сделайте `first` после записи состояния, затем отправьте `secondPrompt` в **новом** чате без истории предыдущего. Для UX введите один и тот же ответ из карточки после первого снимка во всех трёх профилях, даже если первый ответ агента оказался предположением. Так можно отдельно сравнить инициативу агента и качество результата после получения исходных данных.

Сохраните заполненную копию `review.template.json` как `review.json` рядом с проектом. `status` принимает `completed` или `blocked`. При блокировке укажите причину в `notes`. Для каждого пункта `checks` запишите `{"pass": true, "evidence": "команда, цитата или ссылка на артефакт"}` либо `false` с основанием. Для UX вставьте фактический вопрос в `question`. Для восстановления укажите относительный путь записи в `handoffPath`. Неизвестные метрики оставляйте `null`. Отчёт разделяет `PENDING`, `PASS`, `FAIL` и `BLOCKED` и отдельно считает служебные изменения.

UX-кейс оценивает проектное решение и проверяемость его приёмки. Он не проверяет отрисованный интерфейс. Сравнивайте результаты по сценарию, а не по среднему баллу трёх разных задач.

- Четыре теста стенда проверили полный цикл на синтетических результатах, включая лишнюю правку, отсутствие вопроса до проектирования и ложный handoff.

- [Целевая проверка alpha 2 от 4 ноября](alpha2-live-2026-11-04.md) проверила ожидание ответа в Codex CLI и прямой маршрут мелкой правки.
- [Локальная проверка alpha 3 от 6 ноября](alpha3-local-2026-11-06.md) проверила восстановление прерванной установки, pending в чекпоинтах и упаковку интеграции Figma Console.
