# Design Intelligence System

Обобщённый модуль DDH, версия **0.3.0**. DIS — инструмент проектирования воспроизводимой аналитики дизайн-функции. Конкретные организации, источники, исходные выгрузки, измерения, baseline, цели и результаты принадлежат экземпляру измерений в отдельном репозитории данных.

## Состав

- [Спецификация](DIS_v0.3.md) — архитектура, экономические ограничения, сравнения и внедрение.
- [Каталог JSON](metric_catalog.json) — канонические определения 43 кандидатов в метрики.
- [Словарь](metric_dictionary.md) — читаемое представление каталога.
- [Контракт данных](data_contract.json) — JSON Schema 2020-12; `x-semantic-checks` описывают дополнительные проверки pipeline, которые не выполняются обычным JSON Schema validator.
- [Манифест](module.json) — версия, состав и границы модуля.

## Выбор метрик

Каталог включает три контура — Design Performance, Design System Health, DesignOps Efficiency — и сквозные показатели качества данных и экономики. Восемь кандидатов DP01/02/03, DS01/02, DO01/02/03 — предлагаемая отправная точка. Не требуется рассчитывать все 43, не требуется искусственно запускать все восемь до проверки источников. Суммарный «балл дизайна» или рейтинг отдельных сотрудников не предусмотрены. DO03 допускается после проверки трудозатрат.

## Контракт экземпляра

Экземпляр задаёт `instance_id`, scope продуктов/команд/классов работ, IANA `report_timezone`, выбранные метрики, реальные source bindings, владельцев и регламент закрытия периода. `source_types` описывает требования, а не доступность конкретных систем. Для каждой метрики отдельно проверяются схема, воспроизводимость и сопоставимость; причинность и финансовое признание — независимые свойства.

Результат хранит `metric_id`, версию определения/модуля, период, популяцию, исходные batch, числитель/знаменатель, единицу и ограничения. Неизвестное значение остаётся неизвестным с причиной. Значения и цели не включаются в файл определений. Отсутствие продуктовой аналитики блокирует соответствующий расчёт в данном экземпляре, но не превращает результат в ноль.

Финансовые эффекты признаются по уникальному ledger: эквивалент мощности, причинная оценка и реализованные деньги не складываются как независимые выгоды. Аналогично визуальная тематизация UI-kit, связь с библиотекой в исходниках и фактическое использование компонентов в production различаются.

## Статус реализации

Этот пакет содержит определения и контракты. Он не является подключённым ETL, исполняемым набором SQL-расчётов, интерактивным дашбордом или доказательством валидности причинного эффекта. Конкретный pipeline должен реализовать применимые семантические проверки и протестировать расчёты на источниках экземпляра.

## Миграция из v0.2

ID и формулы 43 метрик сохранены. Инвентаризация клиента, численность и привязки к частным репозиториям вынесены в экземпляр. `source_inventory` заменён на `source_types`; `state` — на `readiness_requirements`; `future` — на `source_dependent`; значения и цели удалены из definitions. Часовой пояс больше не фиксируется кодом страны/организации: это обязательный параметр. Data contract version — `0.3.0`. Старые измерения и источники не переписываются; при миграции сохраняются исходные версии и явное сопоставление определений.

## Приём первого пакета данных

[Минимальный intake](intake/README.md) использует существующий data contract: пустой контейнер, карта обязательных полей и preflight для источников одного продукта за завершённый месяц. Он проверяет структуру, хеши и ограниченный набор связей/дат, но не рассчитывает KPI и не заменяет все семантические gates. [Исправление двух version constants report_run](intake/CONTRACT-FIX.md) согласует запись отчёта с корневыми версиями 0.3.0.
