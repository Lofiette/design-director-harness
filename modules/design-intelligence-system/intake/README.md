# DIS: минимальный приём данных

Этот дополнительный модуль принимает первый пакет одного продукта за завершённый календарный месяц. Он использует **существующий `../data_contract.json` 0.3.0** для всех нормализованных сущностей. Формулы и список метрик не меняются. Исходные CSV/XLSX/JSON и исследовательские документы можно принять до нормализации; этот инструмент сам их не преобразует.

## Что передаётся

- `templates/data.empty.json` — структурно корректный пустой контейнер. Пустые массивы означают, что записи ещё не переданы; это не нулевая активность и не значение KPI.
- Фактические raw-файлы — в разрешённом хранилище экземпляра. Фильтр выгрузки, исключения, период, источник, версия и checksum сохраняются.
- Операционный JSON получения файлов содержит `selection`, `source_statuses`, `received_files`. Он описывает выбранный продукт/месяц и наличие файлов; это не альтернативный контракт задач или исследований. Конкретный экземпляр хранит его рядом с данными.

`selection` содержит `product_id` (или `null` до выбора), `selection_status` (`proposed`/`confirmed`), `period` в формате существующего `$defs.period`. Пилотный период — один завершённый календарный месяц в явно заданной IANA зоне.

`source_statuses` связывает source kind из исходного контракта с полями `declared_availability`, `received_status`, `coverage_status`, `coverage_limitations`. Декларация наличия отделяется от получения: `not_received`, `received_unmapped`, `mapped_partial`, `mapped`. Охват: `unknown`, `known_partial`, `known_complete`. Полнота не выводится из отсутствия ошибок схемы.

Каждая запись `received_files` имеет поля `path`, `sha256`, `source_kind`, `source_batch_id`, `row_count`. Путь относительный внутри `--files-root`. `source_batch_id` остаётся `null` до нормализации, `row_count` — `null` до фактического подсчёта. Сохранённый row count проверяется на согласованность с batch, но raw формат не перепарсивается этой версией. Каждый нормализованный batch связывается с отдельным исходным файлом; сложный multi-file источник нужно предварительно явно разбить на batch.

## Нормализация

Для обязательных полей используй [карту существующих полей](FIELDS.md), затем сам data contract. Не изобретай initiative ID, версию DoD, календарь или timestamp для прохождения проверки. Даже nullable поле не означает разрешение скрыть известное значение.

Незаписанное логическое поле нельзя превращать в `false`: например, неизвестная помощь участнику не доказывает самостоятельную попытку. Если исходника недостаточно для строгой строки `research_attempt` или `work_item`, строка остаётся в raw и карте пропусков. Нет необходимости заставлять человека заполнять весь нормализованный JSON вручную.

Задачи выбираются с сохранением исходного фильтра: принятые в месяце могут начинаться раньше. Для оценки потока также нужны незавершённые, отменённые и повторно открытые единицы. Время DoD/финальной приёмки не заменяется текущим статусом без истории. Исходное обязательство не восстанавливается по текущему сроку. Рабочие часы не принимаются равными восьми без календаря.

Попытки исследования сохраняются вместе с протоколом, сценарием, вариантом/версией интерфейса, ролью и псевдонимом участника, порядком попытки, помощью, отказом и критериями результата. AI-предсказания не становятся наблюдениями пользователей. Одна совокупность попыток должна быть явно связана с выбранным продуктом и когортой; эта версия preflight такую связь независимо не доказывает.

## Запуск

Python 3.10+, `jsonschema==4.26.0` — проверенная в этой реализации версия зависимости. Установка и доступ к источникам не выполняются автоматически. Даты проверяются явными функциями стандартной библиотеки, поэтому наличие опционального плагина date-time не предполагается. Неоднозначное смещение `-00:00`, дата без timezone и leap-second timestamps требуют отдельной нормализации по источнику.

```bash
python3 modules/design-intelligence-system/intake/validate_intake.py \
  --data /private/pilot/data.json \
  --intake /private/pilot/intake-status.json \
  --files-root /private/pilot/incoming \
  --as-of 2026-11-22 \
  --output /private/pilot/preflight.json
```

`--as-of` задаёт дату проверки завершённости месяца, не дату исходных событий. При новом результате используй новый путь отчёта: существующий файл с другим содержимым не перезаписывается. Exit 0 означает успешное выполнение preflight, а не готовность KPI; смотри `status`. Exit 2 — ошибка структуры/проверки или недоступный ввод.

## Граница проверки

Реализованы структура существующей JSON Schema с проверкой дат, первичные ключи, ссылки на source batch, хеши raw, перечисленные в коде связи сущностей пилота, выбранный продукт у задач, завершённый месяц и базовый порядок дат. Объём исходных файлов считается фактически; отсутствующий файл не получает нулевой размер как успешный результат.

Это **часть**, а не вся реализация `x-semantic-checks`. Полнота знаменателя, отбор первых валидных попыток, повторные открытия, бизнес-календарь, сравнимость, причины изменений и финансовое признание требуют отдельных проверок. `candidate_for_metric_checks` означает лишь, что основные сущности присутствуют и можно перейти к этим проверкам.

Выход всегда сохраняет `kpi_values: null` и `publication_allowed_by_this_check: false`. DO01 и DP01 рассматриваются первыми по фактической доступности; DO02 — при наличии исходной когорты обязательств. Неизвестные DS, продуктовые и экономические результаты не получают нули. Структурная проверка не изменяет канонический файл измерений.

## Проверки

```bash
python3 -m unittest discover -s modules/design-intelligence-system/intake/tests -v
```

Тесты используют временные синтетические записи, явно помеченные `synthetic`. Они не являются данными какого-либо экземпляра. Включена регрессия исправления версий report_run: metadata 0.3.0 проходят структуру, прежние неверные константы 0.2 отклоняются.
