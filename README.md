# Design Director Harness

**Рабочая среда для продуктовых и инженерных задач в Codex и DeepSeek Harness.** DDH продолжает Product OS 4.1. В одной установке есть процесс ведения задачи, runtime проекта, чекпоинты и выбираемые экспертные пакеты.

[Быстрый старт](#установить-и-обновить) · [Что внутри](#что-внутри) · [Как переносить наработки](docs/SOURCES.md)

## Что внутри

| Часть | Для чего нужна |
|---|---|
| [Пять навыков](#навыки) | Ведут задачу от уточнения до приёмки. Проектная установка добавляет в `AGENTS.md` правило, по которому агент подхватывает этот процесс. |
| [Runtime проекта](#переход-с-product-os-4x) | Хранит задачи, допуски, знания и YAML-чекпоинты в `.cpt/`. |
| [Экспертные пакеты](docs/FULL-INTEGRATION.md#установка-ddh) | Методы для дизайна, исследований, инженерии, рисков и AI. Пакеты выбираются при установке. |
| [Общий установщик](#установить-и-обновить) | Подключает DDH к проекту, выбирает пакеты, обновляет и восстанавливает управляемые файлы. |
| [Чекпоинты задач](#чекпоинт) | Сохраняют контекст для передачи в новый чат. Можно проверить артефакты и увидеть следующий шаг или открытый вопрос. |
| [Figma Console MCP](#подключить-figma-console) | Опциональная интеграция даёт агенту инструменты для работы с документами Figma. Для Codex и DeepSeek Harness есть отдельные настройки. |
| [Стенд проверок](evaluation/README.md) и [реестр источников](sources.json) | Показывают, как сравниваются конфигурации и откуда взяты практики DDH. |

## Как это работает

Например, вы просите перепроектировать форму заявки. Если от типа заявки зависит, какие поля нужны, агент сначала уточняет тип и ждёт ответа. Затем изучает компоненты проекта, описывает состояния формы и определяет, как проверить её поведение. После реализации проверяет сценарий в рабочем интерфейсе. При передаче в новый чат чекпоинт сохраняет результаты и следующий шаг. Для небольшой правки с ясной проверкой агент сразу переходит к работе.

### Навыки

| Навык | Что делает |
|---|---|
| [`ddh-direct`](skills/ddh-direct/SKILL.md) | Уточняет цель, границы и приёмку. Задаёт вопрос, когда ответ изменит решение, и откладывает зависимую работу. |
| [`ddh-decision-audit`](skills/ddh-decision-audit/SKILL.md) | Проводит решение через доказательства: классифицирует неизвестные, оценивает кандидатов по пригодности и глубине, ставит проверку между вердиктом и действием, ведёт журнал решений. |
| [`ddh-design`](skills/ddh-design/SKILL.md) | Проектирует сценарии и состояния, опирается на дизайн-систему, готовит критерии визуальной приёмки и передачу в разработку. |
| [`ddh-verify`](skills/ddh-verify/SKILL.md) | Проверяет результат там, где им будут пользоваться, и сохраняет доказательства и границы проверки. |
| [`ddh-recover`](skills/ddh-recover/SKILL.md) | Сохраняет состояние задачи и при возобновлении сверяет его с текущими артефактами. |

## Установить и обновить

Распакуйте общий ZIP DDH. Архив `ddh-candidate` для кандидата в релиз доступен в [проверках ветки интеграции](https://github.com/Lofiette/design-director-harness/pull/6/checks). Нужен Node.js 22 или новее. С `uv` подготовка зависимостей Python и установка выполняются одной командой из распакованной папки.

```powershell
uv run --no-project --with-requirements product-os/requirements.txt node tools/ddh.mjs install --project "C:/path/to/project" --packs cpt-design-ui
```

`--packs` принимает имена экспертных пакетов через запятую. Без него первая установка включает ядро и пять навыков DDH. После установки откройте проект в новой сессии Codex или DeepSeek Harness. Оба хоста находят навыки через `.agents/skills/`, а инструкции задачи читают из `AGENTS.md`.

Для обновления запустите из новой версии DDH ту же команду с `update` и путём к проекту. При обновлении без `--packs` используется сохранённый выбор. Установщик проверяет управляемые файлы и сохраняет инструкции владельца проекта. С уже подготовленным Python 3.10+ и зависимостями из `product-os/requirements.txt` можно вызвать `node tools/ddh.mjs install` или `node tools/ddh.mjs update` напрямую. Путь к Python задаётся параметром `--python`.

### Проверить runtime в проекте

Из корня установленного проекта запустите:

```powershell
uv run --no-project --with-requirements .agents/ddh-runtime-requirements.txt python -B .cpt/bin/cpt_runtime.py validate
```

Тем же способом запускайте `status`, `checkpoint` и `recover`. Для этих команд достаточно файлов установленного проекта. С подготовленным Python можно опустить `uv run --no-project --with-requirements .agents/ddh-runtime-requirements.txt`.

## Восстановить прерванное обновление

Перед изменением файлов установщик сохраняет журнал с предыдущими и новыми байтами. После остановки процесса запустите команды из папки DDH, указав тот же проект.

```powershell
node tools/ddh.mjs repair-install --project "C:/path/to/project"
```

После восстановления повторите `update` тем же способом, которым запускали его до сбоя. Незавершённая транзакция откатывается к прежним файлам. Для завершённой транзакции команда убирает оставшиеся служебные файлы. Восстановление проверяет владельца блокировки, контрольную сумму журнала, папку проекта и содержимое каждого файла. При обнаружении посторонней правки оно останавливается и сохраняет журнал для сверки.

Если прервать сам процесс восстановления во время записи, остаётся `.ddh-install.recovery.lock`. Требуется ручная сверка файлов с журналом перед снятием этой блокировки. Команда не перехватывает существующую блокировку восстановления. Проверки покрывают остановку процессов, включая конкурирующие команды. Устойчивость к потере питания не проверялась.

## Чекпоинт

Для задачи в CPT используйте её YAML-чекпоинт и проверку `recover --verify-only`. При продолжении DDH читает состояние из `.cpt/`. Команды ниже создают переносимый JSON-снимок артефактов для передачи или ожидания ответа. Из папки DDH запустите команды для проекта. Сначала сохраните входной JSON в проекте как `handoff-input.json` и укажите в `artifacts` существующие файлы относительно корня проекта.

```json
{
  "objective": "Проверить восстановление формы после ошибки",
  "workspace": "project@commit-or-snapshot-id",
  "scope": ["src/form", "test/form"],
  "verification": ["Проверена повторная отправка после отказа API"],
  "unresolved": ["Поведение на мобильной ширине"],
  "next": "Открыть форму на ширине 390 px и проверить фокус после ошибки",
  "artifacts": ["evidence/form-review.md"]
}
```

```powershell
node tools/ddh.mjs checkpoint --workspace "C:/path/to/project" --input handoff-input.json --out "C:/path/to/project/handoff.json"
node tools/ddh.mjs resume --workspace "C:/path/to/project" --input handoff.json --identity "project@commit-or-snapshot-id"
```

`checkpoint` записывает контрольные суммы артефактов. Для `resume` укажите наблюдаемый идентификатор рабочей копии, например текущий commit, который вы записали в поле `workspace`. Команда сверяет снимок и артефакты и выводит сведения для продолжения задачи. Если запись или файл изменились, она останавливается с пояснением.

Для открытого вопроса или незавершённого ревью добавьте поле `pending` в `handoff-input.json`.

```json
{
  "kind": "user_input",
  "request": "Какой сценарий формы должен быть основным?",
  "blockedAction": "Записать design.md"
}
```

Для ревью используется `kind: "review"`. При возобновлении CLI возвращает `waiting_for_user` или `waiting_for_review` в поле `readiness`. Поддерживаются ранние JSON-чекпоинты DDH без `pending`. Для YAML-снимков CPT см. [переход с Product OS 4.x](#переход-с-product-os-4x).

## Подключить Figma Console

В сборку входит [дополнительная интеграция Figma Console MCP](integrations/figma-console/README.md) с закреплённым пакетом `1.46.0`, шаблонами Codex и DSH и ссылкой на переменную окружения для токена. Выберите её при необходимости работы в Figma, затем выполните проверку доступа и Bridge по руководству. Проектная установка навыков включает маршрут работы с этим провайдером.

## Переход с Product OS 4.x

В проекте с валидной установкой Product OS 4.1 и её блоком в `AGENTS.md` выполните обычный `update` из текущей DDH. Команда проверит существующий runtime и добавит управляемые навыки и инструкции DDH. Задачи, допуски, настройки и YAML-чекпоинты остаются в `.cpt/`. Используйте тот же `update` для перехода с прежней проектной установки DDH.

Исходники 4.1 и история доступны в [архивной ветке](https://github.com/Lofiette/design-director-harness/tree/legacy/product-os-4.x) и [теге v4.1.0](https://github.com/Lofiette/design-director-harness/tree/v4.1.0).

## Наработки из других репозиториев

Практика может развиваться в исходном репозитории и затем войти в DDH. Для каждого переноса фиксируем источник и ревизию, проверяем пересечения с существующим процессом и добавляем подтверждение работы в DDH. [Процесс переноса](docs/SOURCES.md) · [Реестр источников](sources.json)
