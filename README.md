# Design Director Harness

**Рабочая среда для продуктового дизайна в Codex и DeepSeek Harness.** DDH подключается к вашему проекту и задаёт, как агент уточняет задачу, принимает проектные решения, проверяет результат и продолжает работу после паузы.

[Быстрый старт](#установить-и-обновить) · [Что внутри](#что-внутри) · [Скачать опубликованный 5.0.0](https://github.com/Lofiette/design-director-harness/releases/tag/v5.0.0)

В этой ветке есть [полный профиль в разработке](docs/FULL-INTEGRATION.md). Он объединяет DDH с runtime Product OS 4.1 и пятью опциональными экспертными пакетами.

## Что внутри

| Часть | Для чего нужна |
|---|---|
| [Пять навыков](#навыки) | Ведут задачу от уточнения до приёмки. Проектная установка добавляет в `AGENTS.md` правило, по которому агент подхватывает этот процесс. |
| [Установщик и пакеты](#установить-и-обновить) | Подключают DDH к проекту, обновляют управляемые файлы и восстанавливают их после прерванной установки. Для каждого хоста есть готовый ZIP. |
| [Чекпоинты задач](#чекпоинт) | Сохраняют контекст для передачи в новый чат. Можно проверить артефакты и увидеть следующий шаг или открытый вопрос. |
| [Figma Console MCP](#подключить-figma-console) | Опциональная интеграция даёт агенту инструменты для работы с документами Figma. Для Codex и DeepSeek Harness есть отдельные настройки. |
| [Стенд проверок](evaluation/README.md) и [реестр источников](sources.json) | Показывают, как сравниваются конфигурации и откуда взяты практики DDH. |

## Как это работает

Например, вы просите перепроектировать форму заявки. Если от типа заявки зависит, какие поля нужны, агент сначала уточняет тип и ждёт ответа. Затем изучает компоненты проекта, описывает состояния формы и определяет, как проверить её поведение. После реализации проверяет сценарий в рабочем интерфейсе. При передаче в новый чат чекпоинт сохраняет результаты и следующий шаг. Для небольшой правки с ясной проверкой агент сразу переходит к работе.

### Навыки

| Навык | Что делает |
|---|---|
| [`ddh-direct`](skills/ddh-direct/SKILL.md) | Уточняет цель, границы и приёмку. Задаёт вопрос, когда ответ изменит решение, и откладывает зависимую работу. |
| [`ddh-decision-audit`](skills/ddh-decision-audit/SKILL.md) | Сравнивает варианты для важных решений, фиксирует основания выбора и способ проверить эффект. |
| [`ddh-design`](skills/ddh-design/SKILL.md) | Проектирует сценарии и состояния, опирается на дизайн-систему, готовит критерии визуальной приёмки и передачу в разработку. |
| [`ddh-verify`](skills/ddh-verify/SKILL.md) | Проверяет результат там, где им будут пользоваться, и сохраняет доказательства и границы проверки. |
| [`ddh-recover`](skills/ddh-recover/SKILL.md) | Сохраняет состояние задачи и при возобновлении сверяет его с текущими артефактами. |

## Установить и обновить

Понадобится Node.js 22 или новее. Скачайте исходники из [релиза 5.0](https://github.com/Lofiette/design-director-harness/releases/tag/v5.0.0) или клонируйте нужный тег. Одна проектная установка обслуживает Codex и DeepSeek Harness через `.agents/skills/`. Укажите путь к существующему проекту.

```powershell
git clone --branch v5.0.0 https://github.com/Lofiette/design-director-harness.git
cd design-director-harness
node tools/ddh.mjs install --project "C:/path/to/project"
```

Команда `install` добавляет навыки и секцию DDH в `AGENTS.md`. Откройте новую сессию в проекте. Секция запускает проверку входных данных для содержательных задач. Если ответ может изменить результат, агент задаёт вопрос и откладывает зависимые правки до ответа. В неинтерактивном запуске он завершает ход сразу после вопроса. Если запрос определён, он приступает к работе.

Обновление берёт файлы из локальной копии DDH, из которой запущена команда. После получения новой версии выполните `node tools/ddh.mjs update --project "C:/path/to/project"` из папки этой версии. Команда сверяет контрольные суммы управляемых файлов и сохраняет остальной текст `AGENTS.md`. При локальной правке навыка, конфликте имён, изменённом блоке DDH или наличии `AGENTS.override.md` команда остановится с пояснением.

Для проектных установок alpha 1–3 используется та же команда `update`. Профиль с отдельным marketplace-плагином обновляется своим способом. После обновления проверьте, какая версия навыков видна в новой сессии.

## Восстановить прерванное обновление

Перед изменением файлов установщик сохраняет журнал с предыдущими и новыми байтами. После остановки процесса запустите команды из папки DDH, указав тот же проект.

```powershell
node tools/ddh.mjs repair-install --project "C:/path/to/project"
node tools/ddh.mjs update --project "C:/path/to/project"
```

Незавершённая транзакция откатывается к прежним файлам. Для завершённой транзакции команда убирает оставшиеся служебные файлы. Восстановление проверяет владельца блокировки, контрольную сумму журнала, папку проекта и содержимое каждого файла. При обнаружении посторонней правки оно останавливается и сохраняет журнал для сверки.

Если прервать сам процесс восстановления во время записи, остаётся `.ddh-install.recovery.lock`. Требуется ручная сверка файлов с журналом перед снятием этой блокировки. Команда не перехватывает существующую блокировку восстановления. Проверки покрывают остановку процессов, включая конкурирующие команды. Устойчивость к потере питания не проверялась.

## Отдельные пакеты для Codex и DSH

Готовые ZIP-пакеты и файл SHA-256 доступны в [релизе 5.0](https://github.com/Lofiette/design-director-harness/releases/tag/v5.0.0). Каждый ZIP распаковывается в отдельную папку со своим адаптером. Для самостоятельной сборки из этой папки выполните команды с Node.js 22 или новее. Укажите новые пути внутри существующей тестовой папки. Сборщик записывает контрольные суммы и отказывается писать поверх существующей папки.

```powershell
node tools/ddh.mjs doctor
node --test test/ddh.test.mjs test/bench.test.mjs test/install-recovery.test.mjs
node tools/ddh.mjs pack --host codex --out "$env:TEMP/ddh-codex-5"
node tools/ddh.mjs pack --host dsh --out "$env:TEMP/ddh-dsh-5"
```

Для Codex зарегистрируйте сгенерированную папку как локальный marketplace в тестовом профиле. Для DSH используйте `.dsh/skills/` сгенерированной сборки в тестовом проекте. Оба пакета включают шаблон `AGENTS.md`. При установке пакета вручную добавьте секцию шаблона в инструкции проекта, чтобы включить проверку входных данных. Выберите один способ установки навыков для проекта, чтобы избежать дублей. [Адаптер Codex](adapters/codex/README.md) · [Адаптер DSH](adapters/dsh/README.md)

## Чекпоинт

Чекпоинт нужен, когда задачу предстоит передать, перенести в новый чат или продолжить после паузы. Из папки DDH запустите команды для проекта. Сначала сохраните входной JSON в проекте как `handoff-input.json` и укажите в `artifacts` существующие файлы относительно корня проекта.

```json
{
  "objective": "Проверить восстановление формы после ошибки",
  "workspace": "project@commit-or-snapshot-id",
  "scope": ["src/form", "test/form"],
  "verification": ["Проверена повторная отправка после отказа API"],
  "unresolved": ["Поведение на мобильной ширине"],
  "next": "Открыть форму на ширине 390 px и проверить фокус после ошибки",
  "artifacts": ["evidence/form-review.md"]
}
```

```powershell
node tools/ddh.mjs checkpoint --workspace "C:/path/to/project" --input handoff-input.json --out "C:/path/to/project/handoff.json"
node tools/ddh.mjs resume --workspace "C:/path/to/project" --input handoff.json --identity "project@commit-or-snapshot-id"
```

`checkpoint` записывает контрольные суммы артефактов. Для `resume` укажите наблюдаемый идентификатор рабочей копии, например текущий commit, который вы записали в поле `workspace`. Команда сверяет снимок и артефакты и выводит сведения для продолжения задачи. Если запись или файл изменились, она останавливается с пояснением.

Для открытого вопроса или незавершённого ревью добавьте поле `pending` в `handoff-input.json`.

```json
{
  "kind": "user_input",
  "request": "Какой сценарий формы должен быть основным?",
  "blockedAction": "Записать design.md"
}
```

Для ревью используется `kind: "review"`. При возобновлении CLI возвращает `waiting_for_user` или `waiting_for_review` в поле `readiness`. Поддерживаются ранние JSON-чекпоинты DDH без `pending`. Для YAML-снимков CPT см. [переход с Product OS 4.x](#переход-с-product-os-4x).

## Подключить Figma Console

В сборку входит [дополнительная интеграция Figma Console MCP](integrations/figma-console/README.md) с закреплённым пакетом `1.46.0`, шаблонами Codex и DSH и ссылкой на переменную окружения для токена. Выберите её при необходимости работы в Figma, затем выполните проверку доступа и Bridge по руководству. Проектная установка навыков включает маршрут работы с этим провайдером. В отдельных пакетах есть и конфигурационные шаблоны.

## Переход с Product OS 4.x

В [архивной ветке](https://github.com/Lofiette/design-director-harness/tree/legacy/product-os-4.x) и [теге v4.1.0](https://github.com/Lofiette/design-director-harness/tree/v4.1.0) сохранён код Product OS. YAML-чекпоинты проекта хранятся локально в `.cpt/checkpoints/`. Сохраняйте их вместе с рабочей копией, если задачи 4.x ещё могут понадобиться.

Чтобы продолжить такую задачу в DDH, проверьте исходное состояние в CPT, затем перенесите в новый JSON-чекпоинт цель, границы, проверенные артефакты, открытые вопросы и следующий шаг. Перенос выполняется вручную. Автоматический снимок перед сжатием контекста относится к CPT 4.x. В DDH снимок задачи создаётся командой `checkpoint` при подготовке передачи или паузы.
